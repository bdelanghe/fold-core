# fold-core

One fold core: one JSON object (a status page, a deck, a page's Markdown) into fold-viewer nodes, in Rust, byte-identical to the
TypeScript fold viewer it was ported from. Pure: no clock, network or filesystem; the caller passes the time and the source files'
text.

    fold(root, opts) -> Vec<(id, Node)>      // insertion order, as the viewer's Map
    from_markdown(md), pages(lines), from_deck(deck), with_sources(value, read)
    walk::walk(nodes, opts) -> Walk               // walk.ts: the artificial viewer's findings, ranked
    walk::verdict(walk), walk::facto_body(...)    // its one line for the page, and its facto Observations
    ax::ax_of(node, path, href, mode, clock)      // fold-ax.js axOf: one fold's accessibility tree; ax::spoken(tree)
    rotor::init(tree, at), rotor::key(tree, state, key, opts)   // Allie's rotor and yank: the next state, and what to say and copy

## WebAssembly

`nix build .#wasm` gives `lib/fold_core.wasm` (a plain C ABI, src/wasm.rs) and `lib/fold-core.ts`, its loader:
`const {fold, walk} = await core(bytes)`: `fold({root, files, opts})` returns the fold list exactly as a golden holds it (`files` maps
each `from` path to its text); `walk({nodes, opts, facto?})` returns `{walk, verdict, facto?}` as a walk golden holds it, where
`opts.budgets` is budgets.json's `budgets` (the walk reads `view.words`) and `opts.localTimeZone` the machine's zone; `ax({node, path, mode, href, localTimeZone?})` returns one fold's accessibility tree
(fold-ax.js `axOf`), `href` naming the links it is given: `"walk"` (`#/a/b`) or `"viewer"` (each id through `encodeURIComponent`). `rotor.init/key/kinds/row` are the rotor and yank
(ax-rebuild briefs/rotor-yank-core.md §6): pure over the host's tree, the host keeping the state between keys and performing the
effects (`say` to the live region, `hint` under the path, `copy` to the clipboard). `nix flake check` runs js/parity.test.ts against
every golden with the built module, and js/rotor.test.ts against the `core` cases of Allie's goldens (goldens/rotor-yank/).

The module carries no zone data. It imports `fold_core.tz_offset(zone_ptr, zone_len, epoch_ms) -> seconds` (`i32::MIN` for an
unknown zone), and the loader answers it from `Intl`, the same zone rules fold.ts reads. A host that loads the module without
`core()` has to provide that import. The default native crate builds the rules in instead (the default `tzdb` feature, chrono-tz).
`checks.wasm-size` holds the module to 200 KB gzipped: it is about 262 KB raw and 115 KB gzipped (it was 2.1 MB raw and 539 KB
gzipped with chrono-tz and regex built in).

## Native library

`nix build .#native` gives `lib/libfold_core.a` and `include/fold_core.h` (generated by cbindgen from src/native.rs), for a host
that links the core in-process (Allie's native tree). The same JSON in and out as the module, with every symbol prefixed:
`fold_core_alloc(len)` for the input, which the call frees; `fold_core_fold_json`, `fold_core_walk_json`, `fold_core_ax_json` and
`fold_core_rotor_json` return a `FoldCoreBuf {ptr, len}` the host frees with `fold_core_free(ptr, len)`; a failure is `{"error": "..."}`. Built without
`tzdb`, it imports `fold_core_tz_offset(zone, len, epoch_ms)` from its host (`INT32_MIN` for an unknown zone). `checks.native` links
native/roundtrip.c against it and runs js/parity.test.ts through it on every golden; `checks.native-header` regenerates the header
and diffs it against the committed one.

## Viewer

`nix build .#viewer` gives the fold viewer as a static app (`viewer/`; step 1 of ~/.lobby/ops/decisions/COGNITIVE-BROWSER-SDK-2026-10-30.md):
`index.html`, `view.js` (routing, the document fetch, the fold), `fold-dom.js` (the DOM from an accessibility tree, from home's
fold-ax.js), the module, its loader as browser JS (`fold-core.js`) and the one face. It holds no data. It fetches one JSON document,
the `fold-data` meta's URL (`/fold-data/fleet/page.json`, from a data path the app is not served from), and the files its `from`s
name relative to it; folds it in the browser with the core; and shows each fold through the core's tree (`ax`, the "viewer" links).
It reads the document again each minute. Served as is: at `/fold/` on phobos by `tailscale serve`.

`checks.viewer` runs `viewer/viewer.test.ts` on every golden: the document fetched from a data URL folds to the golden folds; every
location the viewer links to shows the golden tree; every fold derives its DOM with no refusal (the AX gate); the walk over what it
shows is the golden walk (the load gate). `checks.viewer-browser` (Linux) serves the package at `/fold/` and the `sample` page as its
data, and loads it in headless Chromium at 390×844 and 1024×1366: each location must show the fold the core folds there. It also
fakes `needs.json` and chitin-approve's API, stubs the passkey, and runs the Needs-you flow described next: Enter approves one item,
`]]` steps, and Decline with passkey declines the other.

### Needs you, live, and the sign act

Needs you is read live, not from the page the producer wrote minutes ago (BRIEF-stint-2026-11-02-approve-into-fold;
RECOMMEND-consultant-2026-11-01-reversible-no-approval-and-sign-in-basis S3 and S5). Before folding the fleet's document, the
viewer reads `needs.json` beside it (fold serve's route, below). The core's `needs` entry (src/needs.rs) then:
- takes the producer's sign items out of the Needs-you section;
- puts what waits now first, in a titled group, Approvals. That group is a fold of its own, so it has its own heading.

The other items stay where the producer put them: no group is invented from an id. When the read fails (the host asleep, another
login, no `--needs-as`), Approvals offers nothing to sign, and the notices zone (below) says why. The viewer reads `needs.json` again in four cases: on open,
on going into Needs you, with each minute's refresh, and after every act on an intent.

Each live item is sign.ts's (`needs/sign-<id>`) and has two acts, both the passkey, each a verdict on the item (the brief's
addendum 1). Both are forms carrying `data-intent` and `data-call`, and `viewer/sign.js` `sign` takes them in the page:
- **Approve with passkey** is the item's first act, so Enter on the item runs it, as the rotor's first action does. It uses
  chitin-approve's `GET /approve/v1/challenge/<id>` and `POST /approve/v1/assertion/<id>`, unchanged.
- **Decline with passkey** is the item's second act, its own button. It uses `GET` and `POST /approve/v1/decline/<id>`, the
  path addendum 1 names for chitin-approve's decline. It is signed only when the challenge says `verdict: "decline"`, and an
  approval is never signed when the challenge says otherwise. chitin binds each assertion to its verdict and the item's h, so
  neither can be replayed as the other.

Either way, the script first says the challenge's own recipient, text and h (the frame hash, else the intent's text hash). If those
are not what the item showed, it stops before the passkey; otherwise it runs `navigator.credentials.get` and posts the assertion.
It retries 429, and a 504 on the challenge, but never an assertion. The endpoints are built from the intent's 12-hex id
(`src/needs.rs` `endpoints` and `sign.js` `ENDPOINTS` are one table), never read from a document, and nothing signed comes from the
page's data. fold serve takes no verdict at all.

**Notifications** (addendum 2). When fold serve sends them (`--notify-as`, so `needs.json` says `push: true`), Needs you itself
has two more acts: **Notify me on this device** and **Stop notifying this device**. The script (`sign.js` `notifyHere`) asks the
browser's permission, subscribes with fold serve's VAPID public key (`push/key`), and hands the subscription to `push/subscribe`.
On an iPhone a page gets pushes only once Basis is on the Home Screen, and the act says so. A push shows the item's one line
(`To <recipient>`, never its text), tagged by the item, with no sound or vibration of its own. A tap opens the item's fold in the
viewer, where Approve and Decline are (`sw.js`).

**The notices zone** (the brief's semantic-zones addendum, Bobby: "we have a spot for notifactiuons even if there are none ... we
avoid moving content bewteen semantic zones"). Above the fold is one `aside` landmark, "Notices", which is always there and always
the same height. When it says nothing it says "No notices"; a long notice scrolls inside it. Every notice the viewer makes is said
there and nowhere else:
- the kept copy's "Not updated since…", which the heading is described by;
- what a passkey ceremony is doing and what it did;
- notification results.

`#notice` is its polite live region. So a notice never moves the fold. The browser check measures the zone and the fold before,
during and after each ceremony, and fresh against stale, and requires them unmoved.

An item that has gone takes you back to its group, or to Needs you if it was the last. There a status line (`#said`) says what was
done. Keys: j/k move, Enter goes in (or, on an item, runs its act), h goes back, and `]]`/`[[` step to the next or previous fold
beside the one you are in. From a group that is the next group; from an item, the next item. This is vim's section motion, and it is
path arithmetic (`view.js` `beside`), with no cursor kept. The rotor is the page's own structure: the fold's `main` landmark,
each group's heading and each item's named forms. The worker (`sw.js`) leaves `no-store` requests and `/approve/` to the
network: a kept challenge or a kept list must never answer.

## Pages at real paths

`site({nodes, source, base?, localTimeZone?})` (src/page.rs, `site_json` in the module) writes every fold of a folded document as a
whole page of its own, for a host to serve as static files (BRIEF-fold-render-anywhere-2026-10-30, slice 2). The pages work with JS
off. A fold is at `/fold/<id>/<id>/` (each id one segment, id.rs `segment_of`) in the file `<id>/<id>/index.html`, and a fold that
presents as slides also has `…/@slides/`.

- **Title:** each page's `<title>` names the fold and the path it is in.
- **Links:** moves between folds are plain links in the same tab. Each ends in `#<id>`: going in, the fold's `<h1>`, which a browser
  focuses as it loads; going back up the path, the row you came from. No `autofocus`, which lone flags as focus theft. No `ping`: with no
  `fold sink` deployed, every followed link would POST into a 405; it comes back only when a sink is deployed for a real write.
- **Acts:** a fold's act is a `<form>` named by the fold, posting its cap, call and args as hidden fields to `<base>act/<path>/<act key>`
  with a native submit button, and no script (BRIEF-basis-forms-push-signing-2026-10-31 §1). The passkey (`webauthn`, `approve`)
  GETs the fold's sign page instead, where it has one; with JS on, the viewer runs it in the page (Needs you, live, above).
- **A way back:** a missing fold, one whose data failed to load (`failed`), and a root with nothing in it each show the path (to the
  root at least), one line saying what was asked for and why there is nothing, and, off the root, a link back to it (§5).
- **Ids:** the h1 and each child row have the HTML id of their path under the document; a row is an RDFa `schema:WebPageElement` (`resource="#<id>"`) whose `schema:about` (an empty span's `resource`) is the IRI of the thing it shows (id.rs, brief item 20). The id is the element's; the IRI is the data's; the row is never the data.
- **Stylesheet:** every page links `viewer/fold.css`, the viewer's own.
- **Refusals:** an id no file name can hold (empty, `.`, `..`, or holding `/`) is refused, as is a tree toDom refuses.

`tests/pages.rs` holds every walk case's pages to `goldens/pages/<case>.pages.json`, and `js/parity.test.ts` holds the WASM build to
them. `js/html.test.ts` has lone bless each page's `<main>`. `checks.pages-browser` (Linux, `viewer/pages-check.ts`) loads every page
in headless Chromium with JS off, in five modes: light, dark, both again under `prefers-contrast: more`, and `forced-colors`. Each
page must have the right title, focus its h1 when entered by a link, and have links that land. It must also pass lone's colour
contrast over the colours Chromium computes from fold.css, clear 7:1 under `prefers-contrast: more`, and give every button and field a
visible border. Known findings are in `goldens/pages/known.json`.

The colours themselves are proven before any browser runs them. `tests/contrast.rs` checks `viewer/theme.tokens.json`, a Baobab
pinning, through `src/baobab.rs`:
- light and dark: text 4.5, UI 3;
- light-more and dark-more: text 7, UI 4.5;
- forced: every role is a CSS system colour, and every pair is one the platform guarantees.

The same test writes the fold.css block and `native/Colors.xcassets` (any, dark and Increase Contrast, for Apple hosts).
`js/contrast.test.ts` runs Baobab's own TS over the same pairs, and it must agree.

## fold serve and fold sink

Two processes (src/bin/fold.rs), each on 127.0.0.1 for `tailscale serve` to put at a mount, neither run as root (brief item 27: one
binary holding every read and write was the riskiest call). Neither holds or signs an approval. The viewer runs the passkey in the
page against chitin-approve's `/approve/v1/*` (above), and fold serve only lists what waits.

`fold serve --root <dir> --mount /fold --port <n> [--no-store <prefix>]...` (src/serve.rs) is read-only: GET and HEAD of one
directory's files, and nothing else. It writes nothing, takes no body (413), and answers every other method 405. The one body it
takes is an act's form (`POST <mount>/act/<path>/<act key>`, at most 4 KiB). Without the act flags, that form is read only to be
dropped, and the answer is a page that says acting from here isn't on yet, with the way back (goldens/serve/act.html).

With `--act-as <login> --act-host <host> --act-key <file> --chitin <bin> [--act-seat fold-act] [--act-log <file>]`, the form can
ack, defer or decline a chitin message for that one login (S2: allie-s2-fold-act-write). An act is `{cap, call, args, label}`, `cap`
the capability and `call` the verb, as Allie's cap host names them; its act key is its `id`, else its `call`. Only `cap: "chitin"`
with `call` ack, defer or decline runs (`chitin ack <msg> acting|deferred|declined --to <sender> --as <act seat> --ref fold:<act
id>`), and so does `chitin`/`say` (Bobby 38e765d3, which widens S2 42184457): its act carries an `input`, and the form's one typed line
must be printable ASCII within that input's `maxlength`. Free text on an ack, defer or decline is 422, and so is a bad line. It is
sent once per token, always as seat `fold-act` (`chitin say --as fold-act --meta ref=fold:<act id> <to> <line>`), whatever
`--act-seat` says. Every other pair is 422, including the passkey (`approve`/`sign`, which the viewer runs against chitin-approve). Before
the actor runs, every check must pass:
- the peer is loopback;
- `Tailscale-User-Login` is the login;
- the request came through serve (`X-Forwarded-Proto`, `X-Forwarded-Host`) and is same-origin (`Sec-Fetch-Site`, else `Origin`);
- the form's token (src/act.rs: HMAC over the act id, its fixity, expiry and login, 12 hours) is this server's, current, and for
  the act as it stands.

The act comes from the site's act map (`_acts.json`, written by `site()` and never served), not from the form. Success is a `303`
back to the fold, whose status line then says what was done. A stale token, or a fold that changed, gets the page back with
fresh tokens and nothing done. Each POST leaves one line in `acts.jsonl` (0600); for a say, that line has the text's length and
sha-256, never the text. goldens/serve/acts.json holds every refusal and success, and tools/act-e2e.sh (`checks.act-e2e`) runs
one ack and one say end to end with curl and a stub chitin. More routes run under the same checks (loopback, the login, through
serve, same-origin):
- With `--needs-as <title>`: `GET <mount>/needs.json` is `{as, waiting, push}`. It lists the title's waiting intents from
  `chitin pending --as <title> --json`, read on each request and cut to what is shown (`no-store`, no validator). There is no
  decline route: a decline is a passkey verdict at chitin-approve.
- With `--notify-as <seat>` too (addendum 2), fold serve sends notifications through chitin and keeps no key or subscription
  itself:
  - `GET <mount>/push/key` is chitin's VAPID public key (`chitin push vapid-public`).
  - `POST <mount>/push/subscribe` and `push/unsubscribe` take JSON only. They hand the subscription, cut to
    `{endpoint, keys}`, to `chitin push subscribe`, or take it off with `chitin push unsubscribe`.
  - Every 30 s a watcher reads what waits. For each new intent it publishes one Needs-you record:
    `chitin notify --as <seat> --dedupe needs-you:sign-<id> --url https://<host><mount>/needs/approvals/needs-sign-<id>/ "To <recipient>"`.
    Nothing is sent for an item that leaves. chitin's notify-sink sends the Web Push: VAPID, RFC 8291, one push per item ever,
    coalesced, quiet hours.
  - That url is not a page: no file holds an item's fold, which exists only in the live Needs you. It is a `/fold/` path because
    chitin takes nothing else for a push (no query, no fragment). Both ways of opening it land on the item's row, where Sign and
    Decline are, at the viewer's own location `#/needs/approvals/needs-sign-<id>`:
    - A tap on the push: the service worker (`sw.js` `itemUrl`) maps the path onto the app's scope. On a host that serves Basis at
      its root (`https://basis.<tailnet>.ts.net/`) the `/fold` lead is dropped, so the tap opens `/#/needs/approvals/needs-sign-<id>`.
    - The url opened as a plain link (chitin's say to bobby, the notify outbox): on such a host the request still carries the
      mount, and fold serve answers it with `302 Location: /#/needs/approvals/needs-sign-<id>` (`serve.rs` `viewer_link`).
    - To link to an item by hand, use the viewer location: `https://<host>/#/needs/approvals/needs-sign-<id>` (Basis), or
      `https://<host>/fold/#/needs/approvals/needs-sign-<id>` where the viewer is under `/fold`. `#/needs` is Needs you itself.
  - Each line in the log names the intent, or the push service's host, never the text or an endpoint's path.

goldens/needs/serve.json and push.json hold these routes' refusals and successes, and act-e2e runs them with the stub. The act tools replace
fold-serve's darkhttpd agents (brief items 23-24), which send no ETag, no per-file Cache-Control and no custom headers.

With `--private <prefix>... --private-as <login> --private-host <host>` (Bobby ecc464a7, for a seat's conversation at `seats/`),
everything under a prefix is read by that one login alone: its files, its act route and its comment page. A request must be
loopback, carry that `Tailscale-User-Login` and come through serve to that host (the act checks above, less same-origin, since a
typed URL or a bookmark carries none and a read changes nothing). Anything else gets 403 before the path is looked at, so a
refusal never says whether something is there. Prefixes match whole segments after percent-decoding, with empty segments
dropped, so `seats` covers `/se%61ts/a` and `//seats/a` but not `/seatsx/`. A path that will not decode is held as private.
What it serves is `private, no-cache`, and a `--no-store` prefix inside it stays `no-store`. goldens/serve/private.json holds
each case. A page outside the prefix that links in (a root listing its seats) is the producer's to keep content-free.

| Resource | Cache-Control | Validator |
|---|---|---|
| a path holding `@sha256:` | `public, max-age=31536000, immutable` | strong ETag |
| a page (`.html`, a directory's `index.html`) | `no-cache` | strong ETag `"sha-256:<hex>"`, the file digest (304 on `If-None-Match`), `Last-Modified` |
| a data document (`.json`) | `max-age=60, stale-while-revalidate=240, stale-if-error=86400` | the same |
| any other file (viewer JS, CSS, WASM, fonts, `sw.js`) | `no-cache` | the same |
| a `--no-store` prefix (the Sign fold, pending, presence), every error | `no-store` | none |
| a `--private` prefix (a seat's conversation) | `private, no-cache` | the same as its class |

- Every file also gets `Content-Digest` (the same digest) and `Server-Timing: digest;desc="sha-256:…", asof;desc="…", serve;dur=…`.
- No page names a reporting endpoint or a report-only CSP: nothing is deployed to take them.
- `tests/serve.rs` holds every class's headers in `goldens/serve/headers.json`.

`fold sink --port <n> --log <signals.jsonl> [--per-minute 60]` (src/sink.rs) is append-only, put at `<mount>/_sink`:

- `POST /v` (`text/ping`, from `<a ping>`) logs a ping, with `Ping-From` and `Ping-To`: a view. A prefetch never pings, so it is
  never a view. `POST /report` (`application/reports+json`) logs the reports.
- A request with no `Tailscale-User-Login` is refused (403); each viewer gets `--per-minute` a clock minute, then 429.
- Each record is one JSON line appended to `--log`; nothing is read back or served. `tests/sink.rs` holds its answers and records in
  `goldens/sink/answers.json`.

`tests/fuzz.rs` throws request-shaped bytes at both (`FOLD_FUZZ=<n>` cases a side): neither panics or answers outside its statuses,
serve never serves a byte from outside its root nor writes into it, and the sink logs only what it accepted from an identity.

## basis: a fold as text, for a seat

`basis` is the engine's second binary. It isn't named `fold`, because `/usr/bin/fold` comes first on a Mac's PATH. It reads a
document the way the viewer does and writes nothing (src/basis.rs, src/bin/basis.rs):

    basis read [<path>]... [--doc <file>] [--json]
    basis needs [--doc <file>] [--json]     # basis read "Needs you"
    … [--needs <needs.json>]                # Needs you read live, as the viewer reads it

With `--needs` (a saved `needs.json` answer), the document gets the same overlay the viewer gives it, so
`Needs you/Approvals/<item>` is the same path in both. An act on an intent reads `act: Approve with passkey [approve <id>]`.

The document is `--doc`, else `$BASIS_DOC`, else fleet-map's `~/.local/state/fold-data/fleet/page.json`. A path is a list of
steps joined by `/`. Each step is a fold's id, as written or as its page's anchor writes it, or else its title (case folded),
so `needs`, `"Needs you"` and `needs/needs-ask-0` all reach the same fold. The text shows:

- `@ <path>`;
- `in: <way back>`;
- `# <heading>`;
- one line per row, holding the row's spoken words (ax.rs `spoken`, the words a screen reader says);
- `→ <path>` on a row that goes into a fold. That path is the page's row anchor, and `basis read` takes it.
- `↗ <href>` on a row whose link comes from the data;
- `act: <name> [<act id>]` for acts (`[<call> <intent>]` for an act on an intent).

`--json` prints the fold's accessibility tree instead. `tests/basis.rs` holds every walk golden's folds against
`goldens/basis/<case>.txt`, and checks that every `→` path resolves and is an anchor its page writes.

basis keeps no state of its own. A message goes through chitin as the calling seat, and an ask becomes a row in the file
fleet-map reads. The seat is `--as`, else `$BASIS_SEAT`; chitin is `$BASIS_CHITIN`, else `chitin` on PATH.

    basis say <to> <text> [--in-reply-to <id>] [--ref <path>]          # chitin say --as <seat> --meta ref=basis[:<path>]
    basis ack <msg id> acting|declined|deferred|done [--why <t>] [--ref <a>]
    basis ask --topic <topic> --item <text> --why <text> (--intent <12 hex> | --link <href> [--label <t>]) [--pr <pr>] [--thread <n>]

- `say` refuses an approve-shaped text (`Approve:`, `Sign:`, `Please approve`, …): signing stays on /approve, by `basis ask --intent`.
- `ask` checks the row before writing it:
  - The topic is lowercase letters, digits and `-`.
  - The item and why are one line each, at most 300 chars.
  - The intent is 12 lowercase hex.
  - The link is https or a path from `/`.
  - It has an intent or a link, so the row has a button.
- `ask` then adds the row to `--asks`, else `$FM_ASKS`, else `~/.lobby/ops/needs-you/asks.json`. It writes under a lock and by
  rename, keeps the file's shape, and prints the row's `id`, which is `<topic>-<6 hex of the item's sha-256>`. The id comes from
  what is asked, not from the row's place in the file, and the same ask twice is refused.

## Schema

`schema/node.schema.json` is the fold node types (`Node`, `Kid`, `Step`) as JSON Schema (draft 2020-12), generated from them by
`tests/schema.rs`. An absent field is left out, never null, so optional fields are optional, not nullable. The test fails when the types
change and the file was not regenerated (`FOLD_SCHEMA_WRITE=1 cargo test --test schema`), and every golden's folds must read as the
types and write back the same. A consumer takes it from here instead of defining its own: `cue import jsonschema: schema/node.schema.json`
gives the CUE definitions.

## Goldens

Every input is synthetic (`goldens/fixtures/*.json`, `goldens/walk/fixtures/*.json`). The expected folds and walks come from the fold
viewer's own `fold.ts` and `walk.ts` at the rev in `goldens/REV`, by `TZ=UTC FOLD_SRC=<its source tree> FOLD_REV=<rev> bun goldens/gen.ts`.
Every fold case's folds are walked too (`walk/fold-<case>`), and every walk case's folds go through `axOf` as folds and (when they
present) as slides, with both links, plus a fold with no data (`ax/<case>.ax.json`, one `[id, mode, href, tree]` a line). Regenerate them only on purpose: a diff in them
is a change in behaviour.

## Known limits against JS

A cut through a surrogate pair (a lone surrogate in JS) becomes U+FFFD; `new Date()` is reproduced for ISO-like forms only
(JavaScriptCore's free-form fallback is not); a time with no offset, or a page with no `meta.timeZone`, is read in
`opts.localTimeZone` (UTC when absent) where JS uses the machine's zone; JSON parse error messages in a `from` note differ from
JavaScriptCore's wording. The walk's ranking orders fold ids as ICU does for ASCII; past ASCII it orders by code point (ICU
interleaves; ids are slugs). A fold's `updated` that is not a string reads as "Invalid Date" (JS would read a number as epoch ms).
